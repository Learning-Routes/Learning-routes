# Platform STEP 2: Data, accounts, spaces and roles

Written by the reviewer, 28 October 2026. Start only after Platform STEP 1 is merged. This STEP is built under its rules: `docs/FOUNDATIONS.md` §5–§8, the clean-code gates and the public-repository rules.

## 0. Context

The platform has rules, budgets and one action registry, but no database. `review.submit` writes to a key-value `Store` stand-in, and the API Worker only answers `/health`. This STEP gives it real data, real accounts and real tenancy.

Two independent reviews read the first draft of this STEP before any code. A security review and a data-design review found, among other things:
- a role that could write every table;
- a space id trusted from the input;
- a recursive RLS policy;
- progress that would be orphaned by a new version;
- no protection against concurrent edits.

Every fix is folded in below. Where a point is not certain, the STEP says "verify". Verify against the official docs and record what you found in the PR.

**The stack for this STEP (ADR 0005):**
- PlanetScale Postgres 18;
- Hyperdrive with caching disabled;
- `pg` (node-postgres, at least 8.16.3) with Drizzle's node-postgres driver;
- Better Auth, at least 1.6.22.

Everything runs against a local Postgres 18. Do **not** create PlanetScale, Hyperdrive or Cloudflare resources, and do not ask for keys.

**Not in this STEP:**
- the MCP endpoint;
- Stripe and paid enrollment;
- email delivery;
- the cached Hyperdrive config, and a read-only storefront role on a published-only view;
- the blocks and route map in React;
- operator tools;
- any age field: that is an open owner decision.

## §1. The database, locally and in CI

1. **A local Postgres 18 that mirrors PlanetScale's roles.** `platform/docker-compose.yml` runs one `postgres:18` service on a non-default port, with a named volume. An init script creates:
   - `lr_migrator`, with `BYPASSRLS`, like PlanetScale's default role. It owns the schema and runs migrations. Tests never connect as it.
   - `lr_app`, the Worker's role. It has no `BYPASSRLS`, owns nothing and inherits **no** predefined role. In particular it gets no `pg_read_all_data` and no `pg_write_all_data`: those grant write on every table, and a per-table `REVOKE` cannot take it back. `lr_app` gets only the per-table grants the migrations make, and `ALTER DEFAULT PRIVILEGES` grants it nothing.

   Local passwords are fixed dev values marked local-only, in the compose file only.
2. **CI** runs the same image and init script as a service container.
3. **Hyperdrive locally:**
   - a `hyperdrive` binding `DB`, with `localConnectionString` set to `lr_app`;
   - `nodejs_compat`;
   - a placeholder `id`, with `wrangler deploy --dry-run` still passing;
   - one `placement` constant, expected `aws:us-east-1`.
4. **The schema is split by context from the start:** `apps/api/src/db/schema/{auth,tenancy,content,versions,learning,log}.ts`. One `schema.ts` would pass 300 lines.
5. **Migrations:**
   - Tables, columns and indexes are generated by drizzle-kit and committed under `apps/api/drizzle/`.
   - Policies use Drizzle's `pgPolicy` and `.enableRLS()` where they support what §3 needs.
   - Grants, revokes, triggers and functions go in `drizzle-kit generate --custom` files, so the next `generate` never loses or duplicates them.
   - `pnpm db:migrate` applies them with `DATABASE_URL_MIGRATOR`, a direct connection, never through Hyperdrive. Locally it defaults to the compose URL.
   - A file whose first line is `-- no-transaction` runs outside a transaction, for `CREATE INDEX CONCURRENTLY`.
   - Rule, written in the working agreement: migrations are forward-only and expand/contract. They run before the Worker deploys, and each one works with the previous Worker.
   - Configure squawk to accept an index created on a table made in the same file.
6. **The request's database scope.** `withDb(env, fn)` creates a `pg` client from `env.DB.connectionString`. A mutation runs in one transaction, in three steps: load, a pure decide step in `core`, commit. The **commit is awaited before the response is built**, and only closing the client goes in `waitUntil`. No outside call (AI, email, payments) ever runs inside the transaction. Add a lint or a test that fails if an action's `run` receives anything that can make a network call.
7. **dependency-cruiser:** only `apps/api/src/db/**` may import `drizzle-orm`, `pg` or `drizzle-kit`. Only `apps/api/src/auth/**` may touch Better Auth's tables.

## §2. The schema

**Rules for every table:**
- **Ids are uuidv7**, with Postgres 18's `uuidv7()` as the default. `core` makes ids through an `ids` port when it needs one before the insert.
- **Every time column is `timestamptz`.** `created_at` defaults to `now()`; `updated_at` is set by the repository.
- **A row that belongs to a space carries `space_id`.** Each parent has `unique (id, space_id)`, and each child references it with a composite foreign key, such as `(route_id, space_id) references routes (id, space_id)`. A child's space can then never disagree with its parent's.
- **No foreign key crosses spaces.** Write that rule in ADR 0006.
- **Foreign keys into `routes`, `route_versions` and `enrollments` are `ON DELETE RESTRICT`.** Referential actions run as the owner and skip RLS, so a cascade would wipe student history.
- **Localized columns** are `jsonb` with a check, `app.is_localized(col)`: an object whose keys are a subset of es, en, pt, fr and it. It is one shared immutable SQL function.
- **Money** is a `bigint` in minor units plus a `char(3)` currency, checked against `^[A-Z]{3}$`.

**The tables:**

1. **Better Auth's tables:** `user`, `session`, `account`, `verification`, and `rateLimit` if database storage is used. Generate them with Better Auth's CLI for the Drizzle adapter, then review them. User ids are uuid: configure Better Auth's id generation (verify the option name in the pinned version), and add a test that `user.id` is a `uuid` column. These tables get no RLS. Only the auth module touches them, as §1.7 enforces. `verification` stores hashed tokens (§5).
2. **`user_profiles`:** `user_id` as primary key, `display_name`, `time_zone` (default `'UTC'`), `ui_locale`. FSRS daily limits and streaks need the learner's day.
3. **`spaces`:**
   - `slug`, unique;
   - `name`, localized;
   - `default_locale`;
   - `locales`, a `text[]` with the same subset check, plus `default_locale = any(locales)`;
   - `archived_at`.
4. **`memberships`:** `(space_id, user_id)` unique, with `role` in owner, coeditor, assistant or student. Index `(user_id, space_id)`.
5. **`platform_roles`:** `user_id` and `operator boolean`. Nothing more.
6. **`routes`, the mutable draft:**
   - `space_id`;
   - `slug`, unique per space;
   - `title` and `description`, localized;
   - `source_locale`, `access`, `pricing`;
   - `draft_revision bigint`, bumped on every draft change;
   - `latest_published_version int null`;
   - `forked_from_space_id`, `forked_from_route_id`, `forked_from_version`: plain columns with no foreign key. They record provenance, not a relationship;
   - `archived_at`.
7. **`modules`, `lessons` and `blocks`**, each with `space_id`, its parent and `archived_at`.
   - `position` is a `text collate "C"` fractional-index key, made in `core`, with `unique (parent_id, position)`. Inserting between two items never renumbers the others. Add a property test that a key made between two neighbours always sorts between them.
   - `blocks` carry `kind` and `data jsonb`, validated by `core`'s block schema.
8. **`lesson_prerequisites`:** `(space_id, route_id, lesson_id, requires_lesson_id)`, with the pair as primary key. `core` refuses a cycle, and a property test covers it.
9. **Stable content ids.** A lesson's and a block's id never changes from draft to every snapshot. A publish copies them verbatim.
10. **`route_versions`:**
    - `(route_id, version)` unique, and `space_id`;
    - `snapshot jsonb`: the route, modules, lessons, prerequisites and blocks;
    - `snapshot_format smallint not null`;
    - `content_hash`, `published_by`, `published_at`.

    `core` owns a pure `upcastSnapshot(format, json)`, with a test per format.

    **Immutable, enforced by the database:**
    - `lr_app` gets only `SELECT` and `INSERT`;
    - a `BEFORE UPDATE OR DELETE` row trigger and a `BEFORE TRUNCATE` statement trigger raise an exception;
    - tests try `UPDATE`, `DELETE` and `TRUNCATE` both as `lr_app` and as `lr_migrator`, and all of them fail.
11. **`enrollments`:**
    - a student in a route, with `space_id`;
    - `pinned_version`, with a composite foreign key `(route_id, pinned_version)` to `route_versions`;
    - `status`.

    The pinned version changes only through `enrollment.upgrade`.
12. **`progress`:** `(enrollment_id, lesson_id)`, where `lesson_id` is the stable id, with no foreign key into a snapshot, plus `space_id`. Progress on a lesson missing from the new version is kept but not counted.
13. **`cards`:** `(user_id, item_id)`, per user and content item, independent of the enrollment, so re-enrolling or upgrading never resets them.
    - The columns are `space_id`, `due timestamptz`, stability, difficulty and `fsrs_params_version`.
    - A card is a cache that can be rebuilt from `reviews`. Write a test that rebuilds it.
14. **`reviews`, the append-only FSRS log:**
    - `id`, `user_id`, `space_id`, `card_id`;
    - `review_id`, the client's idempotency key;
    - `rating`, `reviewed_at`, `elapsed_ms`, `state_before jsonb`.

    Indexes: `unique (user_id, review_id)` and `(user_id, card_id, reviewed_at)`. `lr_app` gets `SELECT` and `INSERT` only. Partitioning comes later, not now.
15. **`action_log`, the append-only record of who did what:**
    - `id`, `space_id`, `actor_user_id`;
    - `actor_via`, one of ui, mcp or agent;
    - `agent_run_id null`, `action`;
    - `input jsonb`, with secrets and free text already redacted by `core`;
    - `outcome`, `route_revision null`, `at`.

    `runAction` writes it in the same transaction. Index `(space_id, at)`. `lr_app` gets `SELECT` and `INSERT` only. It is a log: never derive state from it.
16. **Deletion.** Spaces, routes and their content are archived, never deleted. Per-user rows (profiles, memberships, enrollments, progress, cards, reviews) are erased only by `user.erase`, one migrator-run path with a test. Foreign keys from those rows to `user` are `ON DELETE CASCADE`, because only that path deletes a user.
17. **Database names follow `FOUNDATIONS.md` §4b.** A test reads the Drizzle schema and fails on a table that is not a snake_case plural noun, a foreign key not named `<entity>_id`, a time not named `<event>_at`, or a boolean not named `is_<state>`. Better Auth's own tables are exempt.
18. **Check against `core/domain.ts`.** A test builds one row of each table from the zod schema and inserts it.

## §3. Tenancy: two fences

The rule: **a user sees and changes only what their role in a space allows, and everything else does not exist for them.**
- An actor outside the space gets `not_found`, never `forbidden`.
- `forbidden` is only for a member whose role is too low.

### The first fence, in `core`

1. **The permission table.** `core/access.ts` exports `can(role, actionName, via)`:
   - an owner does everything in their space;
   - a coeditor edits routes and content, but not memberships or pricing;
   - an assistant reads routes and their students' progress;
   - a student reads published versions they are enrolled in, and writes only their own progress and reviews.

   Other rules in the table:
   - `membership.add` and pricing changes are `via: "ui"` only, so no agent can do them.
   - The platform operator gets `false` everywhere in this STEP.
   - A table test lists every registered action against every role and every `via`, so a new action without a row fails the build.
2. **The space comes from the row, never from the input.**
   - Each action declares its target resource. `runAction` loads that resource and takes `spaceId` from its row.
   - A `spaceId` in the input must match the row, or the answer is `not_found`.
   - Every repository method takes `spaceId` and filters on it together with the resource id.
3. **Members:**
   - only an owner grants the owner or coeditor role;
   - the last owner cannot be removed or demoted.

### The second fence, in Postgres

4. **RLS on every table that carries `space_id` or `user_id`,** apart from Better Auth's tables. Use `ENABLE` and `FORCE`, except on `memberships`; see 5.
5. **One helper, to avoid policy recursion:** `app.member_space_ids(roles text[])`.
   - It is a `SECURITY DEFINER STABLE` function owned by `lr_migrator`, with `SET search_path = pg_catalog, public`.
   - It returns the spaces where the current user holds one of `roles`.
   - `EXECUTE` is revoked from `PUBLIC` and granted to `lr_app`.
   - `memberships` is `ENABLE` without `FORCE`, so the function can read it.

   Verify that this works on PlanetScale without a superuser, and write the fallback in the PR.
6. **The current user:**
   - Every transaction's first statement after `BEGIN`, on the same client, is `select set_config('app.user_id', $1, true)`.
   - Policies read `nullif((select current_setting('app.user_id', true)), '')::uuid`. A reused pooled connection returns `''`, not NULL, and `''::uuid` would throw instead of matching nothing.
   - The sub-select makes Postgres evaluate it once per query.
7. **Policies, with `USING` and `WITH CHECK` for each command:**
   - `spaces`: `id = any(member_space_ids('{owner,coeditor,assistant,student}'))`.
   - `routes`, `modules`, `lessons`, `blocks` and `lesson_prerequisites`: owner, coeditor and assistant may read. Owner and coeditor may write. Students never see drafts.
   - `route_versions`: members may read. Owner and coeditor may insert.
   - `memberships`: a user reads their own rows, and owners read their space's. The table has **no** insert policy for non-owners.
   - `enrollments`, `progress` and `cards`: `user_id = me`, or `space_id` in the owner or assistant spaces for reads.
   - `reviews`: `user_id = me` for both read and insert.
   - `action_log`: owners read their space's rows; inserts come only from `runAction`.
   - `platform_roles`: a user reads only their own row. No write policy.
8. **`enrollment.create` is the only way to become a student.**
   - The action takes only `routeId`.
   - A `SECURITY DEFINER` function checks visibility first: published, open and free.
   - If the caller has no membership, it inserts one with the hard-coded role `student`.
   - It pins `latest_published_version`, read on the server.

   A paid route in a space the caller cannot see answers `not_found`; one they can see answers `invalid`, until Stripe exists.

### The tests

9. **The two-tenant test,** against the real local Postgres, as `lr_app`:
   - users A and B, each the owner of their own space;
   - every registered action, called by A with B's resource ids, answers `not_found` and changes nothing, including when A passes **her own** `spaceId` with B's ids;
   - the same reads as raw SQL, with `app.user_id` set to A, return none of B's rows, with the `core` check bypassed;
   - raw inserts with B's `space_id` are refused;
   - two transactions run on one client: the second, with no `set_config`, sees nothing;
   - a student of space A cannot read a draft or another student's progress, through actions or through raw SQL;
   - nobody can make themselves owner by any path.
10. **Measure RLS once.** Benchmark a route read with and without RLS, and print the result in the PR. It is not a standing CI gate.

## §4. Repositories behind a port

`core` still imports no database.

1. **Typed repository ports, one per aggregate,** in `core/repos/`:
   - `Spaces`, `Memberships`;
   - `RouteDrafts`, with command methods for its children;
   - `RouteVersions`, read and append only;
   - `Enrollments`;
   - `Learning`, for progress and cards;
   - `Reviews`, `ActionLog`.

   Every method returns a typed result with a closed error union defined in `core`: `not_found`, `conflict`, `invalid`. None accepts a raw filter.
2. **A unit of work:** `repos.transaction(fn)`. Postgres implements it with a Drizzle transaction. The in-memory twin implements it with copy-on-write, discarding the copy on throw. `Ctx` gets `repos`, `clock` and `ids`, and the key-value `Store` is removed.
3. **Optimistic concurrency.** Every draft edit takes `expectedRevision` and answers `conflict` when it does not match. Test an agent and a human editing the same route: the second edit is refused, and nothing is lost.
4. **One contract suite runs against both implementations.** Against Postgres it runs as `lr_app`, with `app.user_id` set. It covers behaviour only; tenancy stays in §3.9. It includes:
   - ordering;
   - uniqueness;
   - immutable versions;
   - the `review.submit` retry;
   - `conflict`;
   - "a throw in the middle of a publish leaves no version row";
   - the upgrade test: publish v1, record progress, publish v2 with one lesson removed and one added, upgrade, then check the progress.
5. **`review.submit` uses `insert … on conflict (user_id, review_id) do nothing returning`,** and on conflict reads the stored result. Remove the `shortcut(Platform STEP 2)` comment.

## §5. Accounts with Better Auth

1. **The version:** the newest that is at least 14 days old, at least **1.6.22**, and with no open advisory in osv-scanner. 1.6.22 fixes an account takeover that combines password sign-up with magic links. Set `emailAndPassword.enabled: false`, with a test.
2. **Mounting:**
   - mount it on Hono at `/api/auth/*`, with the Drizzle adapter on `DB`;
   - `baseURL` and `trustedOrigins` are the app origin only.
3. **Magic link:**
   - set `storeToken: "hashed"`;
   - add an `EmailSender` port, whose dev implementation writes the link to the Worker log;
   - the link opens an app page that says "Sign in as …" and **POSTs** the token to a handler that verifies it. A link scanner or a cross-site page that opens the link verifies nothing, and cannot sign a victim in to another account;
   - leave a comment where social providers plug in later.
4. **Sessions and cookies:**
   - `cookieCache` disabled, so a revoked session ends at once;
   - set the session cookie's name and attributes explicitly. A test asserts the exact `Set-Cookie`: a name starting with `__Host-`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` and no `Domain`;
   - `crossSubDomainCookies` stays off.

   Better Auth may add its own `__Secure-` prefix. If the pinned version does, configure around it and say how in the PR.
5. **CSRF across subdomains.** Creator storefronts on subdomains are the same site as the app, so `SameSite=Lax` alone does not protect it. Every non-GET request to `/api/*` and `/mcp` needs an `Origin` exactly equal to the app origin, through Hono's `csrf({ origin })`. `null` is never trusted. Tests check that:
   - a request with a wrong or missing `Origin` is refused;
   - `/api/*` and `/mcp` are unreachable on the usercontent and storefront hosts.
6. **Rate limiting:**
   - `rateLimit: { enabled: true, storage: "database" }`, on in every mode, not only production;
   - `advanced.ipAddress.ipAddressHeaders: ["cf-connecting-ip"]`, never `X-Forwarded-For`, which a client can set;
   - custom rules for sending and verifying magic links, plus a per-email cap in `sendMagicLink`;
   - a test sends 20 parallel requests and expects at most `max` to pass.

   Verify that the database storage counts atomically. If it does not, say so and propose a Durable Object counter.
7. **The actor comes only from the session.** `Actor.userId` is read from the session by the API, never from a request body. No fake session exists on any production path.
8. **The secret** comes from an env binding: `.dev.vars` locally, which is git-ignored, with a `.dev.vars.example` placeholder.

## §6. The first actions on real data

Each action is registered, has rows in the permission table, writes `action_log`, and is covered by the two-tenant test:

- `space.get`;
- `membership.add`: owner only, `via: "ui"` only, an existing user by id. Email invitations come later;
- `route.create`, `route.get`, `route.list`;
- `module.add`, `lesson.add`, `block.add`, each with `expectedRevision`;
- `route.publish`: one transaction that writes the next snapshot, with its format and hash, and sets `latest_published_version`;
- `enrollment.create`: §3.8;
- `enrollment.upgrade`;
- `review.submit`, moved onto Postgres.

**The seed for English Unlimited.** `pnpm db:seed --owner <email>` runs as the migrator. It creates the space, its locales and one sample route.
- It **refuses** unless the email belongs to an existing user with a verified email. The owner signs in once first.
- It is idempotent.
- It refuses if a different owner already exists, unless `--add-owner` is given.
- Nothing personal is committed.

## §7. The owner's runbook

Write `platform/docs/runbooks/database.md`. Each numbered step is one concrete action, for after the merge. No secret ever appears on a command line or in shell history: each one is read from the macOS Keychain with `$(security find-generic-password -s <name> -w)`. When saving one, `-w` goes last with no value, so it prompts.

1. Create the PlanetScale Postgres 18 database, and choose the region.
2. Create the app role, then apply the per-table grants from the migrations as the default role. Verify whether a dashboard role can be created with no inherited role. If it cannot, create it with SQL; PlanetScale's docs say it then does not appear in the dashboard. Also verify that a SQL-created role can connect through Hyperdrive.
3. Run the migrations with the migrator URL from the Keychain.
4. Create the Hyperdrive config:
   ```
   wrangler hyperdrive create lr-db \
     --connection-string="$(security find-generic-password -s lr-app -w)" \
     --caching-disabled --sslmode verify-full
   ```
   Set an origin connection limit that fits the node's size.
5. Put the config's id in `wrangler.jsonc`.
6. Set the auth secret and URL: `openssl rand -base64 32 | npx wrangler secret put BETTER_AUTH_SECRET`, then `BETTER_AUTH_URL`.
7. Deploy, and check `/health`.
8. Sign in once with your own email.
9. Run the seed with that email.
10. If a branch is ever restored: PlanetScale resets role passwords on restore. Check them, and rotate the app role.
